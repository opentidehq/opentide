## How the work was run (what worked)

- **One workflow per item:** `uc-item-v2.js` runs implement → two verify lenses in parallel (acceptance and invariants and principle; test strength by mutation) → skeptic → fix → recheck. The orchestrator merges, never the agents.
  - Args: `{id, issue, name, branch, scope, resume?, fixResume?, pr?, head?}`.
  - **Edit the `BRIEF` path** at the top of the script to wherever you put `phase1-brief.md`.
  - **One workflow per item:** agent concurrency is capped at about 2 per workflow on a 4-CPU box, and a multi-item workflow starves.
- **Resuming:** `Workflow({scriptPath, resumeFromRunId, args})` with the same args replays finished stages from cache. Add `fixResume` to re-run a fix stage with extra context.
- **Never SendMessage an agent that is running inside a workflow.** It spawns a duplicate agent, and the two edit the same worktree at once. Stop the workflow and resume it instead.
- **Merge procedure:** check that the head contains `origin/integration/unified-core` and that every pull_request CI run is green (CI, Golden, Coverage, Schema, Parity, Oracle, CodeQL, Publish dry run, Docs). Then merge with `merge_method=merge`.
  - After each merge, every other open PR is behind. Re-sync it in a scratch worktree by merging integration in (no rebase).
  - Resolve conflicts as unions. For `Cargo.lock`, take integration's lock and let `cargo check` add the branch's dependencies. Watch for duplicate keys after unions in `Cargo.toml`.
  - Commit with `-F msgfile --cleanup=strip` and the two trailers. Compile and test the affected crates, then push.
- **CI facts:**
  - GitHub sometimes drops push events: check that runs exist and dispatch `ci.yml` and `golden.yml` if they don't.
  - Coverage takes about 25–30 minutes.
  - `get_job_logs` returns only the tail, so the failing test may be cut off. Use `get_check_runs` or a larger tail written to a file.

## Disk (the main operational hazard; about 252 GB disk, roughly 20 GB usable)

- Each item has its own Cargo target pool under `/home/user/wt/.target/<name>`. Use `CARGO_INCREMENTAL=0` and `CARGO_PROFILE_DEV_DEBUG=line-tables-only`.
- A full workspace test build is about 100 binaries of about 75 MB each. More than 4 concurrent builds risks a full disk, and agents stop at the 4 GB floor.
- **Free space by:**
  - running `prune-stale-tests.sh <pool>` (keeps the newest build of each test binary);
  - removing old `lib*.rlib/.rmeta` builds (keep the newest 2 per crate, untouched for 20+ min);
  - deleting verifier pools (`<item>-vs/-va`) after their stage;
  - running `uv cache prune` and `uv cache clean opentide` (each `uv sync` caches a 37 MB opentide wheel).
- A background guard loop that does all of this when free space drops below 5.5 GB worked well. Re-arm it every 2 hours.
