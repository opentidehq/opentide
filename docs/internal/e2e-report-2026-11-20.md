### E2E-1 (major): `new rule --platform crowdstrike` writes a rule that does not validate, and it fails `generate`

**Status: fixed (#1731), verified at `43e56259`.** `new` now writes `verbose` and `detection`; `new rule` → `validate` → `generate` passes for all 13 platforms.

`docs/cli/new.md` says "The new file validates as soon as it is written". For CrowdStrike it
does not. This looks like a regression from the B2 fix (#1663): `validate` now holds
`details.trigger` and `details.outcome` to their allowed values, but `new` still writes `...`.

**Reproduction**

```bash
opentide setup --yes --path w --name W --platform crowdstrike
cd w
opentide new rule --name R --platform crowdstrike
opentide validate
opentide generate
```

**Expected:** `new` writes a valid file (the first allowed value, as the docs say:
`verbose` and `detection`); `validate` passes; `generate` runs.

**Actual:** `new` says `✓ Created objects/rules/r.yaml · 6 placeholders to replace`, then `validate`
exits 1:

```text
error[schema_validation]: configurations.crowdstrike.details.trigger: deploy takes verbose or summary (any case), not "..."
60 │       trigger: ...  # opentide:placeholder
   ╰─ help: write verbose or summary
error[schema_validation]: configurations.crowdstrike.details.outcome: deploy takes detection or incident (any case), not "..."
```

`generate` exits 1 with `✗ docs · 0.0s` and `error: docs: "Rule crowdstrike" does not validate`,
and no other phase printed. Replacing the two values by hand fixes both. The other 12 platforms'
new rules validate.

**Code:** `crates/opentide-cli/src/commands/new/scaffold.rs` (placeholders); the allowed values are
`TRIGGERS` and `OUTCOMES` in `crates/opentide-schema/src/objects/platform/crowdstrike.rs:16,18`.

### E2E-4 (major): the published output schema rejects the dry-run payloads of 6 platforms

**Status: fixed (#1732), verified at `43e56259`.** `api_request` allows a list of `{method, url, body}`; all 13 dry-run documents validate.

`opentide --json commands` publishes the `deploy` schema, whose `RulePayload.api_request` is
`object | null`. `docs/cli/deploy.md` (and the changelog's Upgrade note) say that for Defender for
Endpoint, SentinelOne, CrowdStrike, HarfangLab, Splunk and Carbon Black Cloud it is a **list** of
`{method, url, body}` requests.

**Reproduction**

```bash
# any workspace with a staged rule on one of the six platforms
opentide --json commands > commands.json
opentide --json deploy --dry-run --strategy PREVIEW --all --platform splunk > doc.json
# validate doc.json against commands[path=="deploy"].output_schema, with its $defs
```

**Expected:** the document is valid.

**Actual:** invalid for those six; the dry-run documents of Sentinel, Elastic, Sysdig, Bitdefender,
Graylog, Exabeam and Google SecOps (objects) are valid. The error is at
`payloads.splunk[0].api_request`: the `anyOf` of `object` and `null` does not accept an array.
Real deploy documents are not affected (they carry no `payloads`).

**Code:** `crates/opentide-cli/data/output-schemas.json:6205-6214` (`RulePayload` → `api_request`).
Any consumer that validates the contract rejects every dry-run of six platforms.

### E2E-6 (major): renaming a Splunk rule leaves the old saved search (E6 is not fixed)

**Status: fixed (#1730), verified at `43e56259`.** The old saved search is deleted and listed under `removed`, for a leftover copy and a fresh rename.

`docs/cli/deploy.md#splunks-renamed-rules` says a deploy deletes the copies an earlier name left,
and lists them under `removed`. On Splunk Enterprise 10.6.2.5 it never does.

**Reproduction** (local Splunk, a token for `admin`, `enterprise_security = false`)

```bash
opentide deploy --strategy PREVIEW --all --platform splunk        # creates "Splunk LSASS Dump via Procdump"
# change the rule's name to "... Renamed"
opentide --json deploy --strategy PREVIEW --all --platform splunk
```

**Expected:** the old saved search is deleted and the row's `removed` lists it.

**Actual:** both exist (`removed` is absent, exit 0), so one rule now runs twice:

```text
Splunk LSASS Dump via Procdump          owner admin  app search
Splunk LSASS Dump via Procdump Renamed  owner admin  app search
```

**Cause:** the `search=<uuid>` filter works (listing by the UUID or by `opentide rule <uuid>`
returned both, so the plan's question about the filter is answered: it matches the description
text). The deletion is skipped by the owner filter. opentide creates the search through
`/servicesNS/nobody/<app>/`, but Splunk records the authenticated user as owner: `admin`, with a
token and with basic auth alike (a probe search created by `curl` the same way is also owned by
`admin`). The connector keeps only searches whose owner is `nobody`, so it never finds the copy
it created itself.

**Code:** `crates/opentide-connectors/src/splunk.rs:709`
(`.filter(|entry| entry.key("owner").is_none_or(|owner| owner == "nobody"))` in
`other_saved_searches`).

### E2E-2 (minor): `setup --name` is not trimmed, and an empty name is not refused

**Status: fixed (#1733), verified at `43e56259`.** An empty or all-space `--name` or `--org` exits 2; a name is trimmed.

The plan expects `--name ""` to be refused. `new --name ""` is (exit 2, `usage_invalid_value`);
`setup` is not.

**Reproduction**

```bash
opentide setup --yes --path ws3 --name ""        # exit 0; heading is "# ws3" (the folder name)
opentide setup --yes --path ws5 --name "   "     # exit 0
head -1 ws5/README.md | cat -A
```

**Expected:** a usage error (as `new` gives), or at least the folder-name fallback for a name
that is only spaces.

**Actual:** for `"   "` the outcome line reads `✓ Created     in ./ws5` and the README heading is
`#    $`. An empty string quietly falls back to the folder name, which `docs/cli/setup.md` says is
the default but does not say for an explicit `""`.

**Code:** `crates/opentide-cli/src/commands/setup/run.rs:939-946` (`filter(|name| !name.is_empty())`
with no trim), and the same filter in `setup/files.rs:484,592`.
