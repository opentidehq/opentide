# Catalogs and conformance

Catalogs are data compiled into the binary. The engine does not read them from disk at request time. A workspace override path exists for the Tide field catalog and deprecations (`.opentide/lsp/catalogs/generated/fields.json` and `deprecations.json`, written by `opentide generate schemas`); the bundled files under `catalogs/` are the fallback.

Read `references/highlight-spec.md` before touching `highlights/spec.toml` or a capture name.

## How a catalog is loaded

1. TOML (or JSON for generated Tide fields) lives in `catalogs/`.
2. The engine `include_str!`s it with a path relative to the source file (`../../../catalogs/...`).
3. A `serde::Deserialize` struct matches the file. `#[serde(default)]` on optional arrays.
4. `toml::from_str` (toml 0.8) parses it inside `OnceLock` so each profile is parsed once per process. `Catalog::cached` is the pattern in `opentide-kql` and `opentide-spl`.
5. Tests construct the catalog through that cache. They do not open the TOML themselves unless they are checking the sync script.

Adding a key to a row struct without `#[serde(default)]` rejects every existing file that omits the key. Add the field as `Option` or `#[serde(default)]`, then fill the catalogs.

Do not parse catalogs with `serde_yaml`. Do not switch catalog files to JSON unless the file is already generated JSON (`catalogs/tide/generated/fields.json`).

## KQL and SPL catalogs

| Path | Contents |
| --- | --- |
| `catalogs/kql/core/` | operators, scalar operators, functions, types, evaluate plugins, operator options |
| `catalogs/kql/sentinel/` | tables and columns |
| `catalogs/kql/defender/` | tables and columns |
| `catalogs/kql/azure-monitor/tables.toml` | every Azure Monitor Logs table with its columns (generated) |
| `catalogs/kql/asim/asim.toml` | ASIM schemas, columns, parsers and their parameters (generated) |
| `catalogs/spl/` | commands, command options, fields, datamodels, macros |

KQL profiles are `Core`, `Sentinel`, and `Defender`. Sentinel analysis is the default for a raw `.kql` file. Defender is selected when the Tide field path contains `defender_for_endpoint`. A function that exists only in one profile must not be marked known in the other.

Signatures and operator options are copied from public docs (Microsoft Learn for KQL, Splunk Search Reference for SPL). `scripts/sync_kql_learn_signatures.py` is the generator. Do not invent a parameter the Learn page does not list. Cite the page in the catalog `citation` field when the row has one.

Unknown operators, functions, tables, and commands are diagnostics (`kql_unknown_operator`, `kql_unknown_function`, `kql_unknown_table`, `spl_unknown_command`), not grammar errors. A function row with `deprecated = "<replacement>"` is a deprecated alias Learn names on the replacement's article; the engine warns `kql_deprecated_function` and leaves it out of completion. A scalar operator row with `deprecated` is a legacy spelling Kusto still parses (`containscs`); the engine warns `kql_deprecated_operator` and leaves it out of completion too. `evaluate` calls are checked against `evaluate-plugins.toml`, not functions. `render` parses and warns `kql_render_not_valid`. Control commands warn `kql_control_command_unsupported`.

The `sentinel` profile knows the hand-written Sentinel tables, the Defender XDR tables (the Defender XDR connector streams them into a workspace), every table of the Azure Monitor Logs reference and the ASIM parsers; `defender_for_endpoint` knows the advanced hunting tables. `scripts/sync_azure_monitor_tables.py` (MicrosoftDocs/azure-monitor-docs, CC BY 4.0, plus the columns of Azure-Sentinel's KQL validation schemas, MIT) and `scripts/sync_asim_schemas.py` (Azure-Sentinel's `ASimTester.csv` and parser YAML, MIT) generate the TOML catalogs; regenerate them, never hand-edit. Hand-written columns are merged in, never removed. An unknown table is `kql_unknown_table`: a warning under `sentinel`, an error under `defender_for_endpoint`. Tables a workspace declares in `visibility.toml` (`DeclaredDatasets::from_visibility`, `opentide_core::datasets`) are known, and once it declares any for a platform an undeclared one is `kql_table_not_declared` (warning).

`crates/opentide-kql/src/schema.rs` tracks columns through a query (#112). A documented source (a table of the reference, an ASIM parser) reports only a near miss of a documented column (`kql_unknown_column` with a suggestion): tables gain columns before the reference lists them. After `project`, `summarize`, `distinct` or `count` the query names its columns, so any other name is an error. An unknown source, `evaluate` or an operator whose output naming is not modelled makes the columns open, and nothing below it is reported. `kql_type_mismatch` covers only the operators Kusto does not define for a documented type; read `docs/kql/columns.md` before adding a rule, and verify it against the KQL oracle first.

Slow-query warnings (`kql_where_not_first`, `kql_unscoped_search`, `spl_wildcard`, `spl_leading_not`, and the rest of `opentide_core::codes`) come from the `perf` modules. They are warnings about public query shapes, not style nits. Do not add a warning that contradicts `docs/kql/` or `docs/spl/`.

### SPL CIM data models

`catalogs/spl/datamodels.toml` is generated: `python scripts/sync_cim_datamodels.py --source <splunk/pytest-splunk-addon checkout>` (`--check` compares). It reads `pytest_splunk_addon/data_models/*.json` (Apache-2.0, every CIM model, dataset lineage, field name and expected value) and adds what those files leave out, each with its reason in the script: the base-event fields, the Enterprise Security asset and identity fields on every root dataset, CIM 4.x fields CIM 5 dropped, a few object names and datasets, and the models Enterprise Security adds (`Risk`, `Threat_Intelligence`, ...) as `complete = false`. Never copy `Splunk_SA_CIM` files: it is proprietary. Field names are facts; keep the citations to the CIM manual. Do not hand-edit the TOML.

A row is one dataset: `name` (`Model.Dataset`, the object name `datamodel=` takes), `prefix` (the root dataset, `Processes`), `lineage` (`All_Changes.Account_Management`; a field a child defines is `<lineage>.<field>`), `fields` (the ones the dataset defines; children inherit), `values` (completion only), `complete`. The checks (`crates/opentide-spl/src/cim.rs`) follow precision over recall, because sites add fields and datasets to their CIM models: `spl_unknown_datamodel` and `spl_unknown_datamodel_field` are errors only for a name the catalog lacks **and** that is a near miss (one edit up to five characters, two beyond, a swapped pair counting as one) of one a `complete` model has. Anything else unknown is silent. Expected values are never checked: real add-ons emit values CIM does not list (`reply_code=NXDOMAIN`). A change to the generator or the rules runs `splunk/security_content`'s detections through the engine (see `docs/spl/cim-fields.md`): every error must be a real bug in the detection.

`spl_dataset_not_declared` (`crates/opentide-spl/src/declared.rs`) reads `opentide_core::datasets::current()` for platform `splunk`: `index=`, `sourcetype=` (also `::` and `IN (...)`) in the base search and a `tstats` `where`, and macro calls in the base search before the first pipe. It warns only on `Declaration::Undeclared`, so a workspace that declares no name of a kind is never checked for it. `source=` has no declared kind and is not checked.

`spl_search_operator` (`crates/opentide-spl/src/search_operators.rs`) reports `==`, `<>`, `=>`, `=<`, `!~` and `=~` in an SPL search clause: Splunk accepts them, but the comparison does not do what it says (`docs/spl/search-syntax.md`). Its fixtures are `testdata/conformance/lint/`, which the oracle does not read while the grammar reports `spl_parse_error` on these operators; the forms around them that are valid (`==` in `eval` and `where`, quoted values) are probes in `testdata/oracles/spl/`.

## Elastic catalogs

| Path | Contents |
| --- | --- |
| `catalogs/esql/` | commands, functions, operators, cast types with `applies_to` lifecycle and per-release `versions` |
| `catalogs/eql/` | functions (arity, case-insensitive `~` support), pipes |
| `catalogs/ecs/` | Elastic Common Schema fields: type, level, short description, allowed values (`scripts/sync_ecs_fields.py`, Apache-2.0, `NOTICE`) |

`scripts/sync_esql_catalog.py` and `scripts/sync_eql_catalog.py` regenerate them from a pinned `elastic/elasticsearch` docs commit. Elastic's docs are not EUPL-compatible, so the catalogs keep facts only (names, signatures, arity, versions) and the summaries are written in the scripts. Do not paste Elastic prose into a catalog. The 9.x docs do not list 8.19 or 9.0, so `sync_esql_catalog.py --branches` also reads each release branch (8.19, 9.0 … 9.6) and writes `versions`, the lines that accept each command, function, and cast type (`types.toml`). `esql_unavailable` uses those lists: information when an older supported line lacks a name, a warning when the newest does too, an error only for snapshot-only names. `Lifecycle::after_floor` (first documented at 9.2 or later is missing on 8.19) is the fallback for a row without `versions`.

ECS is never a closed list: elastic-1.0 says field names MUST NOT be checked against one. `opentide-ecs` feeds completion and hover (wired in `opentide-analysis/src/ecs.rs`) everywhere, and a hint where a known field's type makes the query suspicious. The field checks (#116) run only where the query's indices are known and all hold ECS documents (`opentide_ecs::indices_are_ecs`): `logs-*` integration data streams, or names a declared `ecs_indices` pattern covers (`ecs = true` on a log source in `visibility.toml`; a used pattern that only reaches one is not enough). ES|QL reads its indices from `FROM`; kuery, Lucene, and EQL from the rule's elastic block (`index`, or `threat.index` for `threat.query`); a `data_view_id`, an omitted `index`, a raw `.kuery`/`.lucene`/`.eql` file, or one non-ECS pattern in the list means no field check. There:

- `ecs_type_mismatch` (error) only for what Elasticsearch rejects on an ECS mapping. The Lucene and EQL rules are live verdicts in `testdata/oracles/elasticsearch` (`live_elasticsearch_probes.rs` runs the probes again with the ECS checks, and every mapping-dependent probe must then agree); kuery reaches the same field-type errors through Kibana's `match` and `query_string`, and ES|QL's follow the Verifier and the catalog's parameter types. Add a probe for a new rule. The rules: a wildcard, regexp, or fuzzy term on a number, date, ip, or boolean field, and a term the type cannot parse (`source.ip:abc`, `process.pid:[a TO b]`) in kuery and Lucene; `:`, `like`, `regex` on a non-string field, an `in` list of numbers on a string field, a wrong-typed function argument or arithmetic operand, and an object used as a value in EQL; `LIKE`/`RLIKE` on a non-string column and a column a function parameter takes no type of its kind for in ES|QL (columns the query reads straight from the indices, until `STATS` or a command whose columns it does not show). Never: a range on an ip field (valid), `==` on a `text` field or a string compared with an ip in ES|QL (valid), `==` with a string on a number in EQL (converted).
- `ecs_unknown_field` (warning) only for a near miss: under an ECS field set (`process`, `source`, ...), not in ECS, not under an object, flattened, or nested field, no `Ext` segment (Elastic Defend), and one edit (two for names of 16+ characters) from an ECS field, which it suggests. `.text`, `.keyword`, and `.caseless` resolve to their parent. Integration namespaces (`azure.*`, `okta.*`, `winlog.*`), `labels.*`, wildcards, and optional EQL fields (`?x`) are never checked.

`elastic_dataset_not_declared` (warning) checks the block's `index`, `threat.index`, and `data_view_id`, and ES|QL `FROM`, against the `indices` and `data_views` an elastic log source declares, opt-in per kind (`Declaration::Undeclared` only). `crates/opentide-analysis/tests/elastic_detection_rules.rs` runs the ECS checks over every public rule on `logs-*`: any `ecs_type_mismatch` there is an engine bug.

## Tide objects

`scripts/sync_opentide_schemas.py` runs opentide's own generator (`python -m opentide.generation.lsp_catalog`) and writes `catalogs/tide/generated/`, the reference schemas and the highlights key list; it needs an opentide that ships the generator (`uv run --project ../opentide python scripts/sync_opentide_schemas.py` from a checkout). Rows are keyed by schema id; lookups resolve an object's `metadata.schema`, a bare family or unknown revision taking the newest, and a family-keyed catalog (an older workspace one) applying to every revision. Required fields, closed objects and legacy keys come from the catalog: never hard-code a revision check in Rust. `scripts/requirements-opentide.txt` pins the opentide release `pydantic_object_issues.py` uses as its oracle. Pydantic is the CLI authority. The LSP emits the same `{code, field_path, severity}` with ranges. `scripts/pydantic_object_issues.py` is the comparison source. Do not re-encode the object schema as hand-written Rust structs when the generated field catalog already has the answer.

Vocabularies live in `catalogs/tide/vocabs/*.vocab.toml` and load once (`OnceLock` in `vocabs.rs`). An unknown vocab value is `vocab_unknown`. Deprecated fields use the generated deprecation list (`deprecated_field`).

Injection, from `language_for_field_path`:

| Field path | Language |
| --- | --- |
| `configurations.sentinel.query` | KQL |
| `configurations.defender_for_endpoint.query` | KQL |
| `configurations.splunk.query` and legacy `configurations.splunk.search` | SPL |
| `configurations.elastic.query` and `threat.query` | ES\|QL, EQL, kuery, or Lucene from `type` and `language` (`elastic_query_language`) |
| `configurations.carbon_black_cloud.query` | Lucene, Carbon Black dialect |
| `response.procedure.searches[].query` with `system: elastic` | the entry's `language`; none when omitted |
| `response.procedure.searches[].query` with `system:` a platform identifier above | that platform's language and profile, in any key order (`hunt_query_language`) |
| `configurations.splunk.actions.notable.drilldown.search`, any other `query:` / `search:` | none |
| `configurations.crowdstrike.*` | unsupported |
| markdown fields | HighlightSpec `markdown.*`, not a query engine |

Injections come from the YAML structure (`injection.rs` over `yaml_scalar.rs`), not from line prefixes, and carry their real path and their platform. The analysed text is the scalar's value (folded, unquoted, escapes decoded, block indent stripped). Tokens are remapped onto the original YAML coordinates through the byte map. Do not highlight the dedented buffer's offsets. `scripts/oracles/oracle.py` extracts the same paths with PyYAML, and `crates/opentide-tide/tests/query_extraction.rs` holds every `testdata/` object to it.

## Conformance

`testdata/conformance/external/<id>/` holds real public rules and a `.broken.` twin (`frobnicate` or `.show` for KQL, `notacommand` for SPL). `crates/opentide-analysis/tests/external_corpus.rs` does not require the full valid file to parse; the oracle does (see Oracles below), and every rule in the corpus parses today. The test keeps the full rule, finds the longest prefix that parses (at most 16 lines, and the prefix must contain `|`), injects the fault on that prefix, and requires `kql_unknown_operator` or `spl_unknown_command`. The broken full file must produce at least one diagnostic. A corpus that catches the fault on fewer than 5 KQL prefixes or 2 SPL prefixes fails. The Elastic twins (`esql/`, `eql/`, `lucene/`, SigmaHQ conversions under DRL-1.1, listed in `sigma.tsv`) are checked by `crates/opentide-analysis/tests/external_elastic.rs`: every valid file is free of errors and every `.broken.` twin has one. Two verdict tables sit beside them: `lucene-queryparser/cases.tsv` (Apache Lucene's own parser tests, checked by `crates/opentide-lucene/tests/lucene_queryparser_cases.rs`) and `kuery-opensearch-dashboards/cases.tsv` (OpenSearch Dashboards' kuery tests, checked by `crates/opentide-kuery/tests/opensearch_dashboards_cases.rs`, with a `:` → `:)` fault twin per accepted query). Each line is `accept` or `reject`; a disagreement is either fixed or listed in the test's `EXCEPTIONS` with its reason. Sources and licenses are `testdata/conformance/external/SOURCES.md`. Do not add a rule whose license is unclear, and do not trim a public rule down to the prefix the grammar already accepts.

`testdata/conformance/pydantic/` and `crates/opentide-analysis/tests/tide_corpus.rs` check object issues against the opentide CLI's Pydantic models.

## Oracles

`.github/workflows/oracle.yml` compares the engine with Microsoft Kusto.Language, Splunk's search parser, and the Elastic and Lucene parsers (`@elastic/esql`, Elasticsearch's `EqlBase.g4`, Kibana's kuery `grammar.peggy`, Lucene's `QueryParser`; `scripts/oracles/README.md`). The Elastic job also runs every rule in a pinned `elastic/detection-rules` checkout. It runs every corpus query, external rule, perf sample, probe in `testdata/oracles/<lang>/`, and Tide rule query through both sides, and compares catalog names with `GlobalState.Default` and `searchbnf.conf`. `testdata/oracles/exceptions.toml` is the exact ledger of disagreements: an unlisted one fails, and so does a listed one that is gone.

- A grammar or catalog fix that closes a gap deletes its path or name from the ledger in the same change. CI tells you which.
- A new `kql_unknown_column` or `kql_type_mismatch` rule gets a fixture in `testdata/conformance/columns/`; the KQL job requires Kusto.Language, analyzing against the engine's catalogs, to reject it too.
- A new form from a real rule gets a one-line probe in `testdata/oracles/<lang>/`, not a trimmed copy of the rule.
- A `.broken.` twin must break the query for the reference too. Inject the fault on a live line, never inside a comment or string.
- The references are CI-only. Do not vendor Kusto.Language, Splunk, a Splunk SDK, or an Elastic or Lucene parser; the Elastic grammars and jars are fetched by pinned SHA-256 into a git-ignored cache. `scripts/license-scan.sh` checks release artifacts.

## Configuration TOML is not a catalog yet

Issue `#64` (children `#65`–`#68`) will vendor Pydantic JSON Schema for `.opentide/configurations/**/*.toml` after `opentide#374`. Until that pin exists:

- Do not hand-write a JSON Schema, a tree-sitter TOML grammar, or HighlightSpec captures for TOML.
- Do not validate `sharing.toml` inside `opentide-tide`.
- `Cargo.toml` and `catalogs/**/*.toml` are not `opentide-config` documents.

## Checks

```bash
cargo test -p opentide-kql -p opentide-spl -p opentide-tide -p opentide-analysis
cargo run -p opentide-lsp -- generate-highlights --check
```

Schema sync: `python scripts/sync_opentide_schemas.py --check` with opentide installed passes (labels aside, the catalogs match what it generates). The `opentide canary` workflow (`.github/workflows/opentide-canary.yml`) runs it daily against opentide `development` and reports drift in its summary without failing the build: when it reports drift, regenerate with that opentide and commit.
