# opentide-tide — agent guide

Tide YAML objects in the editor: schema and vocabulary diagnostics from the bundled catalog
(`data/catalogs/tide/`), the UUID reference graph, query injection (each platform block's query
analysed by its engine, with positions mapped back), outline, inlay hints and templates.

## Place

domain, tier 0: depends on opentide-core, -ecs, -highlight and every query engine. Used by
opentide-analysis and opentide-lsp. The plan folds it into `opentide-workspace` (§4).

## Invariants

- Pydantic (`src/opentide`) remains the authority for Tide objects: the engine reports the same `{code, field_path, severity}` with real source ranges. `opentide-analysis`'s `tide_corpus` test holds it to that.
- The catalog and templates are generated from the Rust models (`cargo xtask codegen`); regenerate them with the model change.
- No `std::fs` in `src/`; YAML through `opentide_core::node` only (the `yaml` module), the reader `validate` uses: never a second YAML library (#850).
- `is_uuidv4` (`uuid::Uuid::parse_str` plus version 4) is the one object-id check.
- `analyze` is what the editor publishes on top of `validate`'s findings: the queries a block
  carries, the highlighting and the symbols. The blocks themselves are `block_diagnostics`,
  which `opentide lint` reads and the editor does not (UC-2.6, [#821]): a check here that
  `validate` already makes would show the fault twice. `cargo xtask lsp parity --corpus faults`
  compares the two and reports a block finding the server published.

[#821]: https://github.com/opentidehq/opentide/issues/821

## Test

```bash
cargo nextest run --profile fast -p opentide-tide
uv sync --group dev && cargo nextest run -p opentide-analysis -E 'binary_id(opentide-analysis::tide_corpus)'
```

`tests/query_extraction.rs` checks the queries extracted from every object under
`crates/testdata/` against what YAML loads.

## Do not

- Add a check Pydantic does not make without the decision recorded (plan §3, invariant 3).
- Hand-edit `data/catalogs/tide/`.
